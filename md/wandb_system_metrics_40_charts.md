本文把指标定义、截图中直接可见的现象、结合代码作出的推断分开。截图读数均为近似值；本次没有重跑训练或测量优化后的速度。

## 阅读约定与星级

| 星级 | 在本项目中的含义 |
|---|---|
| ★★★★★ | 优先查看：直接帮助定位哪张卡在工作、显存是否紧张、GPU 是否充分展开工作 |
| ★★★★☆ | 重点辅助：解释计算、访存、CPU 等潜在瓶颈 |
| ★★★☆☆ | 常规辅助：结合其他指标才能判断原因 |
| ★★☆☆☆ | 特定问题时查看：通信链路、存储容量、时钟等 |
| ★☆☆☆☆ | 当前 BF16 语言模型任务中通常较少提供新信息 |

星级会随问题变化。例如，磁盘即将写满时，磁盘空间就成为最高优先级；使用 NVLink 的多卡并行任务中，NVLink 流量也会更加重要。

### 先确认图的横轴、颜色和采集范围

- 所有截图横轴都是 **Time (minutes)**，表示 run 的经过时间，单位为分钟，不是训练 step。你的 `wandb.init()` 在训练模型加载之后，所以这里的时间不包含此前所有启动工作。
- 图例明确标出的蓝线是 **GPU 0**，橙线是 **GPU 1**。前 8 张紫线没有显示 GPU 编号，不能仅凭紫色确认对应哪张卡。
- System 图是采样数据。采样间隔、底层硬件统计窗口、曲线聚合和平滑都可能使很短的计算、传输和显存峰值不可见。
- 纵轴通常自动缩放。特别是磁盘空间图，曲线看似大幅跳动，实际变化可能只有几 MB。
- `0`、缺失值、硬件不支持、采集权限不足是不同情况；看到一条长期为零的高级计数器，应先确认它是否可用。

### 本项目中两张卡的职责

当前代码设置 `model_device='cuda:0'`、`server_device=1`：

```text
GPU 0：PyTorch 训练模型，计算 log probability、loss、梯度并更新参数
                        │
                        │ 每轮同步权重
                        ▼
GPU 1：vLLM 模型，生成训练回答和验证回答

一轮主要顺序：同步权重 → 生成回答 → 评分 → 训练更新 → 按需验证
```

该流程在生成和更新阶段交替使用两张卡。因此，两张卡的活动曲线交替出现是可以预期的；不能要求它们始终同时满载。

还要考虑你的 `keep = micro_advantages != 0`：同一组回答奖励完全相同时，减去组均值后的 advantage 可能全为 0，对应 microbatch 会跳过模型前向和反向。因此，GPU 0 的短峰也受到实际奖励分布影响，不能直接由峰的数量推算训练步数。

本地运行元数据记录了两张 **NVIDIA RTX PRO 6000 Blackwell Server Edition**；结合本地环境与运行记录，核对到 W&B **0.26.1**、vLLM **0.19.1**、PyTorch **2.10.0+cu129**。元数据中的逻辑 CPU 数为 208，物理内存约为 1 TB 量级。这些用于解释截图中的单位和比例；截图本身未给出 run ID，因此不能把本地某条运行记录与截图逐点视为同一份原始数据。

## 这组图必须先澄清的采集口径

### A. Process GPU 不等于单个 Python 进程独占的 GPU 资源

W&B 0.26.1 的 NVIDIA 采集器先取得整张卡的功耗、温度、显存等数值，再根据进程关联关系，把相同数值写入 `gpu.process.<编号>.*`。所以 Process GPU Power 不能解释成“只由训练进程造成的功耗”，Process GPU Memory 也不能直接等同于某个 PID 的独占显存。

这一版本还有一个具体实现细节：筛选 GPU 时收集了被监控 PID 的子孙进程，没有把父 PID 本身加入候选集合。你的 PyTorch 模型在训练主进程中，vLLM 在子进程中，因此 Process GPU 面板可能显示 GPU 1 而遗漏 GPU 0。此结论来自固定版本源码，不是根据图的颜色猜测。[W&B 0.26.1 NVIDIA 采集源码](https://github.com/wandb/wandb/blob/v0.26.1/xpu/src/gpu_nvidia.rs)

本次只读检查的本地 `09:01` 运行记录中，确实只有 `gpu.process.1.*` 八项，没有 `gpu.process.0.*`，与截图前 8 图的曲线形态相符。由于图片未展示 run ID 和完整指标 key，逐图对应时仍以面板选中的实际 key 为准。排查两张卡分工时，优先用明确画出 GPU 0、GPU 1 的图 23～30。

### B. PCIe/NVLink 的 Bytes 标题在本版本中不能按累计字节解释

W&B 0.26.1 将 NVIDIA GPM 的 `PCIE_RX_PER_SEC`、`PCIE_TX_PER_SEC`、`NVLINK_TOTAL_RX_PER_SEC`、`NVLINK_TOTAL_TX_PER_SEC` 原样保存到名称带 `Bytes` 的字段。NVML 给这些 GPM 值规定的单位是 **MiB/s**，采集代码没有转换成字节数。

因此，按这套采集路径，图 11 的峰值约 2800 应读作约 **2800 MiB/s**，约 2.73 GiB/s；不能读作“累计传输了 2800 字节”。持续时间和原始采样缺失时，也不能从这根峰直接算出整次权重同步的数据量。[NVML GPM 枚举与单位](https://docs.nvidia.com/deploy/nvml-api/latest/api/group__nvmlGpmEnums.html)

版本升级、手工重命名或其他采集器可能改变口径，所以该结论限定于已核对的 0.26.1 GPM 路径。

### C. 这个 DRAM Active 面板实际映射到带宽指标

0.26.1 把 GPM 的 `DRAM_BW_UTIL` 保存为 `dramActive`。因此本文图 17 按“**显存带宽使用量相对理论最大带宽的比例**”解释。不能因为标题中有 Active，就直接套用别的工具里“显存接口活跃周期占比”的定义。

同样，`Time Spent Accessing Memory` 来自 NVML 的 memory utilization，关注读写活跃时间。两者相关，但分母不同，后文会专门比较。

### D. CPU、RAM、磁盘的数字也有版本与范围差异

本版本常见的 `MB`、`GB` 标签实际按 1024²、1024³ 字节换算，应分别理解为 MiB、GiB。GPU Memory Allocated 的 `Bytes` 则是原始字节数。

另外，W&B 0.26.1 的进程 CPU 图使用进程生命周期平均 CPU 时间比例，再除以采集到的物理核数；默认进程 RSS、线程数和 CPU 统计不自动覆盖整棵子进程树。不能把这个 CPU 百分比与 `top` 的瞬时百分比直接比较。详见图 35～40。[W&B 系统采集源码](https://github.com/wandb/wandb/blob/v0.26.1/core/internal/monitor/system.go)、[gopsutil CPUPercent 实现](https://github.com/shirou/gopsutil/blob/v4.26.3/process/process.go)

## 第一组：截图 1，图 01～06

### 01. Process GPU Power Usage (W)

**重要性：★★★☆☆。核心用途：观察设备负载的阶段变化，辅助判断长时间等待。**

功耗是设备在单位时间内消耗能量的速率，单位 W，即 J/s。这里是被 Process GPU 筛选选中的整卡功耗，不是模型参数的功耗，也不是整台服务器的总功耗。

**你的截图：**启动时约 85～100 W，随后多在 270～310 W，最高约 350 W，并多次落回 90～140 W。可以确认负载存在明显阶段切换；低谷可能是等待、同步、评分或训练/生成交接，单凭功耗不能指定其中某一种原因。

功耗高通常说明设备执行了更多工作，但它也受频率、指令类型和访存方式影响。没有达到 600 W 不代表配置错误。若需要总能耗，应对功耗随时间积分，例如稳定 300 W 运行 1 小时约为 0.3 kWh，不能把 W 直接当成电量。

**对照：**图 02 是同一功耗按上限归一化；图 03 提供上限；图 23 能同时观察两张卡。[NVIDIA 功耗定义](https://docs.nvidia.com/deploy/nvidia-smi/#gpu-power-readings)

### 02. Process GPU Power Usage (%)

**重要性：★★★☆☆。核心用途：判断当前功耗距离允许上限还有多远。**

在这里可按 `功耗百分比 = 当前功耗 / 当前功率上限 × 100%` 理解。分母来自功率限制，而不是理论 FLOPS，也不是 GPU 计算单元数量。

**你的截图：**多数时间约 45%～52%，最高接近 60%。结合图 03 的 600 W，上下两图可以相互核算：300 W / 600 W = 50%。

这张图方便跨不同功率配置比较相对负载。但两张 GPU 都显示 50%，实际瓦数、吞吐量和能效可能完全不同。若功率限制在运行中变化，同样的瓦数也会显示不同百分比。

**对照：**图 01/02 的信息大部分重叠；图 08 的 Utilization 与这里的百分比不是同一件事。图 24 是每张卡各自的功耗百分比。

### 03. Process GPU Enforced Power Limit (W)

**重要性：★★☆☆☆。核心用途：提供功耗分母，检查功率配置是否变化。**

这是功耗管理当前执行的功率上限。上限规定设备允许的功耗范围，不要求设备一直消耗到该值。

**你的截图：**上限稳定在约 600 W。图 01 大部分只有约 300 W，因此截图没有显示“实际功耗持续贴近上限”的形态。曲线平直在这里是合理现象。

如果实际功耗长时间接近该上限，同时 SM 时钟下降，可以进一步查功率限制原因。仅看这条水平线，无法判断是否发生过限功率，也不应据此调整硬件功率设置。

**对照：**图 25 是两张卡的上限；图 22 的时钟变化有助于解释功率限制是否影响运行。[NVIDIA 功率上限说明](https://docs.nvidia.com/deploy/nvidia-smi/#gpu-power-readings)

### 04. Process GPU Memory Allocated (Bytes)

**重要性：★★★★☆。核心用途：判断所选设备显存使用量与容量余量。**

表示所选 GPU 上 NVML 报告的已用显存，单位为字节。它包含驱动能看到的设备内存占用，不能直接等同于 PyTorch 的 `torch.cuda.memory_allocated()`，也不是模型权重文件大小。

**你的截图：**启动后很快升到约 `9×10^10～1×10^11` 字节。注意 `1×10^11` 字节 = 100 GB（十进制），约 93.13 GiB（二进制）；不能直接称为“100 GiB”。

对于 vLLM，高显存占用可能包含预分配的 KV cache、模型、运行缓冲和通信缓冲。你的 `gpu_memory_utilization=0.9` 提供了显存预算，但并不是对整张卡强制生效的绝对上限。不能仅凭显存大就认定模型过大或内存泄漏。

**对照：**图 05 换成容量百分比；图 26 明确区分两张卡；图 06 关注读写活动而不是占了多少空间。[vLLM 显存预算参数](https://docs.vllm.ai/en/v0.19.1/configuration/engine_args/#--gpu-memory-utilization)

### 05. Process GPU Memory Allocated (%)

**重要性：★★★★☆。核心用途：快速判断所选 GPU 的显存余量。**

它是 `已用显存 / GPU 总显存 × 100%`。与图 04 使用相同的容量信息，只改变展示单位。

**你的截图：**启动后长期处于约 90%～接近 100%，并出现周期性小幅起伏。这提示该设备显存余量有限，后续增加生成并发或额外缓冲需要测量峰值；它本身不等于已经 OOM。

例如，显存容量为 96 GiB 时，95% 占用只剩约 4.8 GiB；但真正能否完成下一次分配还受当前分配器状态、其他进程和瞬间峰值影响。截图采样不能替代峰值显存统计。

**对照：**图 04 更适合算还剩几 GiB，图 05 更适合一眼看压力；排查当前两卡配置优先看图 27。

### 06. Process GPU Time Spent Accessing Memory (%)

**重要性：★★★☆☆。核心用途：辨认显存读写活跃阶段。**

这是底层采样期间 GPU 全局显存发生读或写的时间比例。例如 70% 表示该统计窗口内约 70% 的时间存在显存读写活动。它不表示用了 70% 的显存容量，也不能直接换算成“达到了 70% 的最大带宽”。

**你的截图：**多数时间约 60%～75%，在若干位置落到接近 0。结合功耗和 GPU Utilization 的低谷，可以推测这些时段设备工作减少；要定位到具体代码阶段，需要对齐日志或计时。

高读写活跃比例不是天然坏事：模型执行本来就需要读取权重和中间状态。判断是否受访存限制，还应结合图 17、图 18、图 20 与实际 token/s。

**对照：**图 28 是每张卡的同类指标；图 17 在本版本是 GPM 带宽比例，两个百分比不能互换。[NVIDIA utilization.memory 定义](https://nvidia.custhelp.com/app/answers/detail/a_id/3751/~/useful-nvidia-smi-queries)

## 第二组：截图 2，图 07～12

### 07. Process GPU Temperature (°C)

**重要性：★★★☆☆。核心用途：排查温度与降频的关联。**

表示所选 GPU 温度传感器的读数，通常是 GPU 核心温度，不能据此推断显存芯片或每个热点的温度。

**你的截图：**温度从约 30°C 升至 44～47°C，之后随负载在约 39～47°C 间波动。这组读数没有表现出持续升温失控的趋势；没有证据仅凭这张图把速度问题归因于过热。

温度响应有滞后，负载降低后不一定立即降温。判断热限制应对照设备自身的温度阈值、实际时钟和 throttle 原因，不能给所有 GPU 套一个统一温度界线。

**对照：**图 29 更适合比较训练卡与生成卡；与图 22 的 SM 时钟一起观察，比单看温度更有解释力。

### 08. Process GPU Utilization (%)

**重要性：★★★★☆。核心用途：查看所选 GPU 是否持续有 kernel 执行。**

该指标统计采样窗口内有 GPU kernel 正在执行的时间比例。100% 表示窗口内几乎一直有 kernel 在运行，不保证所有 SM、CUDA Core 或 Tensor Core 都被充分利用。

**你的截图：**多数时间接近 100%，中间多次跌到 0～10%。这说明所选卡的计算任务经常持续运行，也存在短暂停顿。它与图 06 同时下降时，等待或阶段切换是值得检查的方向。

### 13. GPU Tensor HMMA Active (%)

## 第四组：截图 4，图 19～24

### 19. GPU Streaming Multiprocessor (SM) Occupancy (%)

**重要性：★★★★☆。核心用途：判断 GPU 内部是否有足够多的并发 warp。**

SM 是 GPU 执行线程块的计算单元。warp 是 NVIDIA GPU 组织线程执行的基本单位，通常包含 32 个线程。Occupancy 关注的是：**实际活跃、驻留的 warp 数量，相对于硬件允许同时驻留的最大 warp 数量的比例**。

“驻留”不代表这些 warp 每个时钟周期都能执行指令；它们也可能在等待数据或依赖。这个百分比的分母不是 SM 数量，也不是所有 CUDA Core 的数量。

**你的截图：**GPU 1 橙线经常只有约 2%～7%；GPU 0 蓝线大部分为 0，计算峰时约 28%～30%。这提示生成卡的并发 warp 数较少，值得与图 20、batch 配置和算子一起看。

例如，一个 SM 最多能驻留 64 个 warp，实际只有 4 个，那么这个时刻 occupancy 约为 `4/64=6.25%`。最大可驻留数是举例，不是对当前 GPU 的规格断言。

低 occupancy 可能来自任务较小、寄存器或共享内存限制、kernel 设计等；高 occupancy 也不保证更快。优化目标是降低耗时、提高有效吞吐，而不是把这个数字单独推到 100%。[CUDA Occupancy 说明](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#occupancy)

**对照：**图 20 关心 SM 是否忙，本图关心里面驻留多少 warp；两者同时看才有意义。

### 20. GPU Streaming Multiprocessor (SM) Active (%)

**重要性：★★★★★。核心用途：比整卡 Utilization 更细地看 SM 活动覆盖程度。**

可将它理解为：在采样窗口内，对各 SM 的忙碌程度作时间和空间上的平均。一个 SM 有活跃 warp，就可以被视为忙碌；因此它比“整张卡是否至少有 kernel 在执行”更细。

**你的截图：**GPU 1 橙线长期约 60%～75%，GPU 0 蓝线大部分接近 0，间歇达到约 80%～90%。它清楚地展示了生成卡较持续地工作、训练卡短时间集中工作的分工。

假设一块 GPU 有 100 个 SM，整个窗口都只有 10 个 SM 忙碌，则整体 GPU Utilization 仍可能接近 100%，而 SM Active 只约 10%。这只是说明两个指标分母不同，不是对你的硬件 SM 数量的描述。

SM Active 较高说明工作覆盖较广或持续较久，但仍不意味着每个周期都在完成高效浮点运算。若同时 occupancy 和 Tensor 活动较低，仍可能存在较少并发工作或等待。

**对照：**图 30 看整卡忙碌时间，图 19 看 warp 驻留程度，图 18 看 Tensor 指令活动。本图是理解这三个层次的重要连接点。

**重要性：★★☆☆☆。核心用途：辅助判断显存时钟状态是否发生变化。**

它表示 NVML 报告的显存工作时钟，单位 MHz。频率是硬件运行状态，显存带宽则是数据传输能力，两者相关但不能只靠这个数字直接换算；还涉及显存类型、接口位宽和传输机制。

### 32. Disk I/O Utilization (MB)

**重要性：★★★☆☆。核心用途：定位集中读取或写入的时段，辅助解释启动、保存和数据访问。**

虽然标题有 Utilization，本版本这里显示的是每个块设备自监控起点以来的**累计读写量**，按 1024² 字节换算，实际单位为 MiB。它不是磁盘忙碌时间百分比，也不是 MiB/s。

**你的截图：**`md0` 的读累计量在约第 10～12 分钟大幅增加到 40000 多 MiB；写累计量则逐步增长到 30000 多 MiB。一段水平线表示这段时间没有明显新增 I/O，并不是磁盘已经停止被系统使用。

如果想计算平均读取速率，应取两个采样点的差：`(后一个累计读数－前一个累计读数)/经过秒数`。例如 100 秒内增加 10000 MiB，平均就是 100 MiB/s。

注意 `md0`、物理盘和分区可能存在设备层次关系，同一笔 I/O 可能在多个层次被计数，不能把所有线简单相加。此外这是设备范围的统计，不能把图中的全部读写都归给训练程序，或根据它反推数据集大小。

**对照：**图 33/34 是已经占用的存储空间。本图累积的写入量可以很大，而空间净增长很小，因为可能在覆盖、删除或反复改写文件。

表示被监控文件系统的空间使用比例。不要把这里的 70% 理解成磁盘的读写速度达到了性能上限的 70%。文件系统保留空间等机制也可能影响百分比口径。

### 35. Process CPU Threads In Use

**重要性：★★☆☆☆。核心用途：了解被监控进程的线程数量及其变化。**

表示进程拥有的操作系统线程数量，不是正在同时运行的线程数，也不是占用了多少 CPU 核。线程可能在运行、等待锁、等待网络或休眠。

### 40. Process CPU Utilization (%)

**重要性：★★★★☆。核心用途：辅助识别主进程 CPU 工作，但必须理解本版本的平均与归一化方式。**

W&B 0.26.1 调用的 `CPUPercent()` 使用进程自启动以来的累计 CPU 时间，再按进程存活时间求平均；W&B 随后除以检测到的物理核数。因此本版大致是：

```text
显示的 CPU 百分比
  = 100 × 进程累计 CPU 秒数 / 进程存活秒数 / 物理核数
```

这里“累计 CPU 秒数”可以累加多个线程的 CPU 时间；如果两个线程同时各运行 1 秒，就可能累计约 2 CPU 秒。因此它与墙钟时间不同。

**你的截图：**最初约 2%，随后接近 0。结合本地记录的 104 个物理核，若一个执行线程在整个统计历程中持续占满一个逻辑 CPU，显示值也仅约 `100/104=0.96%`。若只在短阶段忙碌，其余时间等待 GPU 或 HTTP，长期平均会更低。

所以它不是最近 15 秒的瞬时 CPU 使用率；短时 CPU 峰可能被长期平均稀释。默认也不合计所有 vLLM 子进程。因此不能根据这条近零曲线认定整个训练任务没有 CPU 瓶颈。

按物理核数归一化也不意味着所有环境中 100% 都是硬上限，超线程等因素会影响解释。需要进一步确认时，应看具体 PID、线程和子进程的区间 CPU 使用率，而不是直接与 `top` 的百分比比较。

**对照：**图 35 是线程数量，本图是消耗的 CPU 时间；GPU 侧图 30 则是 kernel 执行活动，三个分母不同。[W&B CPU 汇总实现](https://github.com/wandb/wandb/blob/v0.26.1/core/internal/monitor/system.go)、[gopsutil 生命周期平均计算](https://github.com/shirou/gopsutil/blob/v4.26.3/process/process.go#L358)

| SM Active，图 20 | 各 SM 忙碌程度的时空平均 | 工作覆盖较广或较持续 | 驻留 warp 足够多、每周期都有效计算 |
| SM Occupancy，图 19 | 驻留 warp 数 / 最大可驻留 warp 数 | 有较多并发 warp 可供调度 | 指令无等待、性能一定更好 |
| Tensor Pipeline，图 18 | SM 执行 Tensor 运算的活动时间 | Tensor 运算参与较多 | FLOPS/峰值同样高 |
| DRAM Active，图 17 | 本 GPM 路径下的显存带宽使用量 / 理论带宽 | 显存数据传输较多 | 容量占满或已经确定受带宽限制 |
| Time Spent Accessing Memory，图 28 | 显存读写活跃时间 / 统计时间 | 读写比较持续 | 达到了同样比例的峰值带宽 |
| Memory Allocated，图 27 | 已用显存容量 / 总显存容量 | 剩余容量较少 | GPU 正在计算 |
| Power Usage，图 24 | 实际功耗 / 当前功率上限 | 功耗接近允许上限 | 模型有效吞吐高 |

可以用一个简化例子理解：GPU 持续执行一个较小 kernel，它涉及许多 SM，但每个 SM 只驻留少量 warp，主要等待或搬运数据。此时 **GPU Utilization 高、SM Active 较高、Occupancy 低、Tensor Active 低** 可以同时成立。不要要求这些百分比彼此相等，也不要把它们相加。

### 3. 三种“显存使用率”必须分开

```text
图 27 Memory Allocated：显存空间装了多少数据？
图 28 Accessing Memory：有多少时间在读写显存？
图 17 DRAM Active：当前 GPM 口径下，用了多少比例的显存带宽？
```

举例：模型和 KV cache 常驻在显存中，等待下一轮请求时，容量占用可以为 95%，而读写时间和带宽使用都接近 0。请求到来后，容量几乎不变，后两项却可能迅速升高。

因此，“显存已用 95%”与“GPU 正在执行 95% 的工作”没有直接对应关系。你截图中 GPU 0 的高显存占用与低利用率正好说明这一点。

### 4. 功耗、功率上限、时钟、温度是一组辅助证据

以截图中的数值为例：`300 W /600 W =50%`，描述的是功耗比例。与此同时 GPU Utilization 可以为 100%，因为这个 100% 表示采样窗口里一直有 kernel。

| 联合现象 | 可以先考虑什么 | 还要确认什么 |
|---|---|---|
| 利用率、SM Active、功耗一起降，显存容量仍高 | 等待、阶段交接、没有提交计算任务 | 是否对应生成结束、评分、同步或其他 CPU 工作 |
| 功耗持续贴近上限，SM 时钟下降 | 功率管理可能影响频率 | 驱动限制原因、实际阶段耗时 |
| 温度持续升高，SM 时钟下降，耗时增长 | 散热或热限制可能影响性能 | 该硬件阈值、驱动限制原因 |
| 时钟稳定，但 Tensor 活动低、DRAM 比例较高 | 可能工作粒度小或访存较重 | batch、序列长度、算子和实际吞吐 |

这些是排查方向，不是仅凭两条线就能确定的结论。当前图中的温度和时钟没有给出明显的持续热降频迹象。

### 5. HMMA、Tensor、FP16/FP32/FP64 不按模型 dtype 简单对应

| 对比 | 主要区别 | 在你的图中如何理解 |
|---|---|---|
| HMMA 与 Tensor Pipeline | 特定 Tensor 指令类别与更广的 Tensor 活动 | 形状接近，可先保留图 18，再按需看图 13 |
| FP16 Pipeline 与 Tensor Pipeline | 普通 FP16 运算与 Tensor 运算路径 | 前者为 0、后者有峰，完全可能同时成立 |

| FP32 Pipeline 与 FP32 输入 | 执行路径与数据格式不是同一概念 | 某些 FP32 输入的矩阵乘可能使用 Tensor 路径 |
| FP64 与其他管线 | 双精度普通运算通常不是本任务主路径 | 接近 0 通常无需关注 |

要准确回答“某层到底使用什么指令、耗时多少”，需要算子或 kernel 级分析，System 概览面板提供的是线索。[Nsight Compute 指标与分析说明](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html)

### 7. GPU 显存、进程 RAM、系统 RAM、磁盘各自解决不同问题

| 资源 | 对应图 | 关注的问题 | 常见误读 |
|---|---|---|---|
| GPU 显存 | 04/05、26/27 | 模型、KV cache、激活和缓冲能否放下 | 当成主机 RAM，或认为空闲计算必然释放显存 |
| 进程 RAM | 37/38 | 被监控进程在主机上驻留了多少数据 | 当成全部子进程或整个训练任务的总占用 |

| 系统 RAM 比例 | 39 | 整体内存压力 | 全归因于当前训练程序 |

### 8. 线程数很多与 CPU 百分比低不矛盾

图 35 是“有多少个线程”，图 40 是“消耗了多少 CPU 时间”。线程可能大部分在休眠或等待；本版 CPU 百分比又经过物理核数归一化和生命周期平均。

因此，图 35 约 230 个线程、图 40 接近 0，不足以说明线程配置过多，也不足以排除某个阶段的单核瓶颈。应定位具体阶段、PID 和线程后再判断。

### 结合当前代码的解释与待验证假设

当前 `training_step.py` 中，训练卡为 GPU 0，vLLM 卡为 GPU 1；生成、训练以及验证是分阶段执行的。这与截图中的两卡交替活动相符。

生成部分的配置是 `B=32`、`G=8`，一轮计划生成 `N=B×G=256` 条训练回答；当前实现按 prompt 逐次调用 `server.generate_completions([prompt], sampling_params)`，其中 `sampling_params['n']=G`，前一个调用返回后才开始下一个。也就是说，不能把“每轮 256 条”理解成“同时把 256 条都提交给 vLLM”。这个实现方式使生成阶段的有效并发值得优先检查。

训练使用梯度累积，`gradient_accumulation_steps=32` 对应名义 microbatch 大小 8；随后还会按 `advantages != 0` 筛选。整组奖励相同会使组内中心化 advantage 为 0；筛选后没有有效样本的 microbatch 会跳过计算。因此，只有每轮采样数量还不足以推断训练卡实际做了多少前向和反向工作。

验证每 10 个 step 执行一次，配置为 1024 条样本，通常还会增加生成卡的工作量。含验证的步间隔与纯训练步间隔不应直接混合比较。

据此，可以优先提出两个待验证的方向：**生成阶段是否占用了大部分墙钟时间，以及实际有效训练样本是否较少。** 当前图形与这些方向相符，但还没有给出各阶段的准确耗时，所以不能据此宣布瓶颈已经确定。

### 为什么不能凭这些图判断 W&B 是否拖慢训练

System 图展示的是资源状态，没有提供“同一配置关闭 W&B 后的耗时”。GPU 空闲低谷也可能来自评分、同步、串行请求、验证或其他等待，不能全部归因于日志。

若要判断开销，应在相同配置和相近样本长度下，比较相同阶段的稳定耗时，并把初始化与验证分开。当前代码不是每个 token 都上传日志：常规训练标量按配置每 40 步记录，验证则有自己的日志频率。不过，仅凭这个频率仍不能精确量化 W&B 开销。

### 比继续增加 System 面板更有价值的记录

| 建议记录 | 能回答的问题 |
|---|---|
| 权重同步耗时 | `/pause`、权重传输、缓存处理和恢复一共用了多久？ |
| rollout 生成耗时 | 一轮主要时间是否消耗在生成？ |
| 生成的总 token 数和 token/s | 两轮耗时差异是否只是回答长度不同？ |
| 评分与数据准备耗时 | GPU 的低谷是否来自主机端工作？ |

| 非零 advantage 样本数、跳过的 microbatch 数 | 为什么 GPU 0 的工作峰较少？ |

这些是后续可自行添加的测量建议，本文没有修改代码。GPU 执行有异步性，若用 Python 时间戳衡量某段 GPU 计算，应明确是否等待设备完成；CUDA event 或合适的同步边界能避免把“提交任务很快”误认为“执行很快”。测量本身也可能扰动运行，因此优先测少量有代表性的 step。

### 优先保留哪些面板

若主要关心“为什么慢、哪张卡在等、会不会 OOM”，可以按以下顺序查看：

2. **图 27/26 显存比例与字节数**：判断容量压力及能否尝试更大工作量。
3. **图 20 SM Active、图 18 Tensor Active**：确认忙碌是否对应较充分的计算活动。
4. **图 17 DRAM Active、图 19 Occupancy**：进一步区分访存与并发方面的线索。
5. **图 23 功耗、图 29 温度、图 22 时钟**：辅助排除明显的功率或温度变化。
6. **图 40 CPU、图 38 进程 RAM、图 34 磁盘空间**：按实际症状查看主机侧资源，并确认统计范围。

Process GPU 与每卡图、功耗 W 与百分比、显存字节与百分比有大量重叠。日常可以优先看最能回答当前问题的几个面板，出现异常再展开其余图。

### 采样点之间并不是完整的执行轨迹

已核对的 W&B 0.26.1 默认系统采集间隔为 15 秒；GPU 高级 GPM 指标在每次采集时使用相隔约 200 毫秒的两个样本计算。**一个约 200 毫秒的窗口，不能代表两个图上采样点之间每一毫秒的状态。** 基础 NVML 指标又使用各自的内部统计窗口，CPU 图在本版本还采用生命周期平均。

这会带来三个实际限制：短时权重传输可能完全漏采；较短的训练峰可能只出现一个点；折线把点连接起来，并不意味着中间状态一直平滑变化。因此，不能仅凭截图准确计算每阶段耗时、累计传输量或证明某张卡整段都没有工作。[W&B 0.26.1 采样设置](https://github.com/wandb/wandb/blob/v0.26.1/wandb/sdk/wandb_settings.py)、[NVML GPM 采样接口](https://docs.nvidia.com/deploy/nvml-api/latest/api/group__nvmlGpmFunctions.html)

若显式更改采样设置、启用 DCGM、升级 W&B 或改变驱动，尤其需要重新确认高级指标的单位和口径。本文 PCIe/NVLink 的 MiB/s 与 DRAM 带宽解释限定于前面核对的 GPM 路径。
