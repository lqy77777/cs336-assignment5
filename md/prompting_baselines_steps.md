## 4. 读取题目，并提取最终标准答案

每一行 JSON 都是一道题，包含两个字段：

| 字段 | 含义 |
|---|---|
| `question` | 要交给模型的问题 |
| `answer` | 数据集提供的参考推理和最终答案 |

参考回答的结构是：

```text
参考推理过程……
#### 18
```

评分函数的 `ground_truth` 应当只接收最终答案，例如字符串 `"18"`。

提取逻辑可写成：

```python
ground_truth = example["answer"].rsplit("####", 1)[1].strip()
```

读取时检查分隔符是否存在；如果数据不符合预期，应报告该记录，而不是静默把整段推理当成最终答案。

**先检查 1～3 条记录：** 打印问题、原始参考回答、提取后的最终答案，确认对应关系正确。

## 5. 构造三种提示词

每道题都需要分别填入三种模板的 `{question}`。

| 实验名称 | 模板文件 | 评分函数 |
|---|---|---|
| `question_only` | `question_only.prompt` | `question_only_reward_fn` |
| `r1_zero` | `r1_zero.prompt` | `r1_zero_reward_fn` |
| `r1_zero_three_shot` | `r1_zero_three_shot_gsm8k.prompt` | `r1_zero_reward_fn` |

### 当前模板的转义字符需要先检查

本次静态读取发现：两个 `r1_zero` 模板包含字面量 `\n`，`question_only` 模板中的 `boxed` 前包含两个反斜杠。读取文本文件不会自动把这些内容解释为 Python 字符串转义。

针对当前模板，可以在填题前进行定向处理：

```python
template = template.replace(r"\n", "\n")
template = template.replace(r"\\", "\\")
prompt = template.format(question=question)
```

第一行将字面量 `\n` 转为真实换行；第二行将两个反斜杠转为一个。模板中的 `{{}}` 由 `.format()` 处理为 `{}`。

这一步只作用于原始模板，再填入问题，不要对题目文本或模型回答统一进行这类替换。避免使用无差别的转义解码，误改文本或数学符号。

打印构造后的完整 prompt，检查：

- 问题确实替换到了 `{question}` 的位置。
- `r1_zero` 的 `User:` 和 `Assistant:` 之间有真实换行。
- 两个 CoT 模板最终以 `Assistant: <think>` 结尾。
- 三样本版本仍完整包含原有三个示例。
- `question_only` 的格式指令中显示一个反斜杠的 `\boxed{}`。

**不要把当前题目的标准答案填进 prompt。** 标准答案只供后面的评分使用。

## 6. 设置生成参数

按照 Section 3.4 使用以下配置：

| 参数 | 设置 | 含义 |
|---|---|---|
| `temperature` | `1.0` | 不通过温度额外调整概率分布 |
| `top_p` | `1.0` | 不做 top-p 截断 |
| `max_tokens` | `512` | 最多生成 512 个新 token，不包括 prompt |
| `n` | `1` | 每道题生成一个回答 |
| `seed` | 例如 `0`，并记录 | 控制采样随机性；不承诺跨环境完全复现 |

当前封装通过字典索引读取 `temperature`、`max_tokens`、`n`、`seed`，这四个键都要提供。

两个 CoT 提示词另外设置：

```python
sampling_params["stop"] = ["</answer>"]
sampling_params["include_stop_str_in_output"] = True
```

`question_only` 不使用这两个设置。建议为每种提示词单独构造参数字典，避免上一个实验的停止字符串残留。

### 当前代码没有转发 top_p

`vllm_utils.py` 中 `generate_completions()` 构造 HTTP 请求的 `payload` 时，没有加入 `top_p`。因此，仅在 `sampling_params` 中写入 `top_p=1.0` 不会把它传到服务端。

正式实验前需要确认服务端实际使用 `top_p=1.0`。如果选择显式转发，可在请求的 `payload` 中增加：

```python
"top_p": sampling_params.get("top_p", 1.0),
```

这只是后续实现时的修改建议，本步骤文档没有修改辅助代码。不要把“调用端字典中有这个参数”当作“服务端已收到”的证明。

## 7. 启动一次服务，先生成一道题

建议用 `VLLMServer` 管理服务：

1. 创建对象，指定模型、`gpu=0`，保持 `load_format="auto"`。
2. 在 `try` 中调用 `server.start()`；它会加载模型，并等待服务就绪。
3. 调用 `server.generate_completions()`，传入已构造好的提示词列表和采样参数。
4. 从返回对象的 `.text` 读取回答。
5. 在 `finally` 中调用 `server.stop()`，关闭自己启动的服务。

不要把每道题的生成都包成“启动模型 → 生成 → 关闭模型”。服务应当持续运行，处理多个批次和三种提示词，实验结束后再关闭。

返回值是 `list[VLLMCompletion]`，其中每个对象包含：

| 属性 | 用途 |
|---|---|
| `text` | 保存并送入评分函数的生成文本，不包含输入 prompt |
| `token_ids` | 记录生成 token 数，可使用 `len(token_ids)` |
| `finish_reason` | 辅助判断正常结束还是达到长度上限等情况 |

当 `n=1` 时，返回结果与输入提示词一一对应。检查返回数量是否与输入数量一致。

`batch_size` 控制每个 HTTP 请求包含多少条提示词，不是训练批大小。单题验证时用 `1`，随后可以尝试 `8` 或 `16`，再根据实际显存和吞吐调整。

**完成标准：** 能看到一个真实的模型回答，能确认它回答的是刚才输入的问题。答案暂时错误或格式不规范，并不自动说明调用代码有问题。

## 8. 调用配套评分函数

评分时传入：

- `response`：模型返回的完整生成文本，即 `completion.text`。
- `ground_truth`：第 4 步提取的最终标准答案。

评分函数返回一个字典：

| 键 | 含义 |
|---|---|
| `format_reward` | 是否满足当前评分器的格式要求 |
| `answer_reward` | 解析后的答案是否被判断为正确 |
| `reward` | 总奖励；本题中等于 `answer_reward` |

先用自己编写的简单文本验证“已知正确、已知错误、格式不符”三种情况，再对真实模型回答评分。这是检查接口用法，不是修改评分标准。

**注意当前评分器的严格条件：** `r1_zero_reward_fn` 检查生成文本中是否含有精确的 `</think> <answer>`，其中有一个普通空格，并且要求有 `</answer>`。如果模型在两个标签之间只生成换行，也可能得到格式奖励 0。

因此，保留原始输出很重要。不要为了提高评分，先修复标签、替换空白、补全答案，再把修改后的文本作为原始结果评分。后面可以通过人工复核分析这种解析限制。

## 9. 从小批量扩展到完整评估

按以下顺序推进：

1. **单题验证：** 检查模板、返回值和评分接口。
2. **约 10 道题的小批量运行：** 三种提示词都跑一次，检查批量映射、保存和统计逻辑。
3. **正式运行：** 对相同的完整评估集分别运行三种提示词。

正式比较时固定模型、数据集、题目顺序和生成配置，仅按实验设计改变提示词及配套停止规则。记录实际使用的随机种子和批次大小。

小批量运行只用于调试，不把它的准确率当作完整评估结论。正式结果应报告实际评估题数；使用当前完整测试集时，每种提示词应有 1319 条结果。

建议先把每个批次的输出和评分保存到磁盘。即使之后修改统计或分析方式，也可以复用已经生成的结果，避免重复占用 GPU。

### 建议保存的逐题字段

建议每种提示词保存一个 JSONL 文件，每行对应一道题的一次回答。

| 字段 | 用途 |
|---|---|
| `example_id` | 定位题目、关联不同提示词下的结果 |
| `prompt_name` | 区分三种实验 |
| `question` | 原始题目 |
| `ground_truth` | 提取后的标准答案 |
| `prompt` | 实际发给模型的完整输入 |

| `format_reward`、`answer_reward`、`reward` | 评分结果 |
| `finish_reason`、`num_generated_tokens` | 辅助分析生成是否被截断等情况 |

模型名称、数据集路径、种子、批次大小和实际生成参数，可以另外保存在本次运行的配置文件中。

## 10. 统计题目 (a) 要求的指标

对每种提示词分别统计以下三类，不能把三种提示词混在一起计数：

| 类别 | `format_reward` | `answer_reward` | 自动评分所反映的情况 |
|---|---:|---:|---|
| 第 1 类 | 1 | 1 | 格式通过，答案判为正确 |
| 第 2 类 | 1 | 0 | 格式通过，答案判为错误；仍需排查解析或比较问题 |
| 第 3 类 | 0 | 0 | 格式没有通过，无法据此断言数学答案一定错误 |

至少汇总：评估题数、三类数量、自动评分准确率、格式通过率。

```text
自动评分准确率 = answer_reward 之和 / 评估题数
格式通过率 = format_reward 之和 / 评估题数
```

对于当前两个评分函数，正确回答也会得到格式奖励 1，因此自动评分准确率也等于“第 1 类数量 / 评估题数”。总奖励均值等于答案奖励均值，不要再把格式奖励加进去。

可以附加记录达到长度上限的比例、平均生成长度，帮助分析；这些不是截图单独要求的必交指标。

建议汇总表：

| 提示词 | 题数 | 第 1 类 | 第 2 类 | 第 3 类 | 自动评分准确率 | 格式通过率 |
|---|---:|---:|---:|---:|---:|---:|
| `question_only` | 待填 | 待填 | 待填 | 待填 | 待填 | 待填 |
| `r1_zero` | 待填 | 待填 | 待填 | 待填 | 待填 | 待填 |
| `r1_zero_three_shot` | 待填 | 待填 | 待填 | 待填 | 待填 | 待填 |

自查：每种提示词的三类数量之和，应等于该实验的评估题数；如果不相等，检查漏记、重复或异常评分。

## 11. 人工检查被自动判错的回答

题目明确要求至少观察第 2 类中的 10 个例子，并对第 3 类进行同样的检查。建议对每种提示词分别检查这两类，各抽至少 10 条；如果某一类不足 10 条，就全部检查并说明实际数量。

固定抽样方式或随机种子，并记录检查了哪些 `example_id`。

每条记录需要判断：

1. 模型的最终答案按数学意义是否正确？
2. 如果实际正确，自动评分为什么失败：没有提取到答案、格式严格匹配失败，还是答案等价性比较失败？
3. 如果确实错误，是计算、理解题意或其他问题？
4. 如果回答没写完，是否达到 512 token 上限？无法判断时明确标为无法判断。

人工复核表可以使用：

| 提示词 | example_id | 自动类别 | 标准答案 | 人工判断 | 评分失败或错误原因 | 输出证据 |
|---|---|---|---|---|---|---|
| 待填 | 待填 | 待填 | 待填 | 正确／错误／无法判断 | 待填 | 保留原文片段 |

报告检查数量和结论，例如“抽查第 2 类 m 条，其中 k 条实际正确”。不要把少量人工抽样直接写成“整个测试集准确率已修正为某值”，也不要将人工判断覆盖原始自动评分记录。
